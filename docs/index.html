Ranking Content Pages for Refresh Review

Muhammad Omer Siddiqui · FlyRank ML Internship Capstone · 2026
Lane: Refresh / Content Opportunity Scoring

Abstract

Content teams cannot review every page, so they need a ranked list of which pages to look at first. This project builds that ranked refresh-priority queue on the FlyRank ML Internship anonymized starter dataset (30,000 pages, 32 clients). A transparent hand-written baseline is compared with Logistic Regression, Decision Tree, and Random Forest under a client-holdout split. Learned models improve Precision@50 over the baseline on the same data and the same metric. The output is decision-support only: a ranked action playbook with reason codes for human editors — not automatic publishing, and not a claim about Google’s ranking algorithm.

1. Introduction / Problem

FlyRank helps brands grow organic visibility. A recurring operational problem is simple but expensive: which existing pages should an editor review first for refresh, expansion, CTR improvement, or monitoring?

Looking at pages randomly wastes limited editor hours. Missing a high-demand declining page lets visibility keep falling. This work turns search and content signals into a ranked review queue so humans spend time where it is most likely to matter.

The decision supported is: “Open these pages first this week.” The action is human review — not automatic rewrite or publish.

2. Data

Release used: FlyRank ML Internship starter dataset (data/raw/content_refresh_anonymized.csv).

  • 30,000 rows · one row = one content page
  • 32 pseudonymized clients
  • Trailing 90-day search and engagement metrics

Work also referenced the gated warehouse release on Hugging Face for data-contract practice (FlyRank/internship-warehouse), but modeling and validation reported here use the starter slice so results are fully reproducible from the public repo.

Excluded (public-safe):

  • Client names, domains, real URLs, titles, raw keywords (not present; never reconstructed)
  • Product decision flags (health_score, priority_score, action_type)
  • trend_direction / trend_pct as model features (they define the label only)

3. Methodology

Label (proxy)

is_declining = 1 when trend_direction == "down", else 0. This is a current-window proxy label, not a true future outcome.

Features

Volume (impressions, clicks, sessions), position, age, freshness, CTR, engagement, word count, content type, and related tiers. No label-derived or product-flag features.

Baseline

Transparent rule score:

0.40×visibility + 0.30×freshness_risk + 0.25×position_opportunity + 0.05×depth_gap

Reason codes include stale_visible_page, declining_with_demand, and low_ctr_visible_page.

Models

Logistic Regression, Decision Tree (max depth 5), Random Forest.

Validation

Client-holdout split (~20% of clients held out). No page from a test client appears in training. Compared against a random row split to show the honesty gap. Primary metric: Precision@50, always next to the base rate.

Leakage checks

  • Forbidden columns (trend_direction, trend_pct, label) absent from the feature matrix
  • Deliberate leak test: adding the label as a feature inflates the score; removed before any claim
  • No product scores used as features

4. Results

On the same client-holdout split, learned models beat the hand-written baseline on Precision@50. Random Forest is typically strongest. A random-row split often looks better — that gap is partly client memorization, so the client-holdout number is the honest one.

Exact table numbers come from the executed notebooks work/notebooks/w05_model.ipynb and work/notebooks/w06_validation_audit.ipynb. Re-run those notebooks to refresh metrics; they use fixed seed 42.

False positives in the top of the list are often high-impression pages that are stable or rising. Volume signals are strong, so human context (seasonality, consolidation) remains required.

5. Limitations & honest framing

What this work can claim: observed ranking quality on held-out clients; directional decision-support for editors.

What it cannot claim: that refreshing causes traffic recovery; that it predicts Google’s algorithm; production readiness without human review; results on the full ~79M-row warehouse without re-validation.
  • Label is a current-window proxy, not a future outcome
  • Starter 30k slice, not the full warehouse
  • Unbalanced client history in broader warehouse data requires careful windows

6. Ranked recommendations (action playbook)

Final score blends model probability with the transparent baseline (0.70×model + 0.30×baseline and attaches reason codes and actions:

ActionWhen reason codes suggest it
refreshStale + visible, or declining with demand
refresh_and_review_ctrVisible position with low CTR
monitorLower priority — watch only

Human review before acting: check real demand, seasonality, sibling consolidation, recent edits, and whether low CTR is normal for intent.

Do not automate: auto-publish, auto-delete, causal claims from the score alone, or rollout to new clients without re-checking client-holdout performance.

Queue construction lives in work/notebooks/w07_action_playbook.ipynb (exports regenerate under work/outputs/).
